# 07 · 导入对账与去重

## 1. 流水线

```
选文件 → 解码（UTF-8 优先，失败回退 GBK——微信/支付宝导出为 GBK）
      → CSV 解析（引号/逗号/Tab/转义）
      → 规范化 NormalizedRow（保留原始行 JSON 快照）
      → 去重分级 → 预览（新增/跳过/建议）
      → 用户确认 → 过账（TxBuilders.expense/income + externalId）
```

## 2. 幂等与去重（三层）

| 层 | 判定 | 动作 |
|---|---|---|
| 1. 稳定外部 ID | sha256(parserId \| accountId \| 交易号或行内容) 完全一致 | **跳过**（同一行重复导入永远幂等） |
| 2. 指纹 | 同日±1 天 + 同金额 + 同币种 + 同方向 + 对手方规范化（去空白/大小写/括号注记）一致 | **仅建议**：提示"疑似重复，可能与 tx:xxx 重复"，用户裁决 |
| 3. 转账对 | 同批次内：一出一进、金额一致、日期差 ≤2 天、不同账户 | **建议合并**为一笔转账（一次经济事件） |

设计红线：**同日同商户同金额可能是真实的两次消费**——指纹层永远不自动删除，只生成带依据（指纹值、原交易 id）的建议，可撤销。

## 3. 通用 CSV 模板

表头（必填 date/type/amount，可选 time/counterparty/merchant/note/txid/transaction_id）：

```csv
date,time,type,amount,counterparty,note,txid
2026-05-01,12:30:00,支出,35.50,美团外卖,午餐,202605011230001
2026-05-02,09:00:00,收入,20000.00,某公司,工资,202605020900001
```

- type：`支出/收入` 或 `out/in`
- 日期 `yyyy-MM-dd` 或 `yyyy/M/d`；金额含千分位可解析
- **txid 列强烈建议**：有交易号即走第 1 层精确幂等

## 4. 微信/支付宝适配（框架已就绪，待真实样本校准）

`ImportService.parseGenericCsv` 已覆盖通用形态；两家的列名差异（如支付宝"商品说明/金额（元）/收支"，微信"交易时间/金额(元)/收/支"）在阶段 2 用脱敏真实样本校准列映射后注册为专用 parserId。**未校准前不承诺两家原生格式直接可用**——先把账单导出为上方通用模板即可使用全部功能。

## 5. 双通道一笔经济事件的合并示例

支付宝余额支付 200 元（支付宝账单"支出"）+ 同日银行卡扣款 200 元（银行流水"支出"）：
- 若都按消费导入 → 消费 400（错，重复一次）；
- 管线识别转账对 → 建议记为"支付宝→银行卡 转账 200"或按实际方向"银行卡→支付宝"，**消费 0、现金净变动 0**。
- 保守起见自动默认为"建议"，由用户确认方向。

## 6. 对账（reconciliation）

- 每月复盘流程：导入 → 处理建议 → 对比**真实余额**（App 内查询银行）与账本余额 → 差额走"对账调整"（单列，不进收支）→ 差异原因（漏记/重复/在途）记录在备注。
- 期初补录只对"开户时已存在"的资产使用；此后余额修正一律走对账调整。
- 只维护余额快照、没有完整流水的账户：月报明确标注"无法还原该账户的消费/收益明细"。

## 7. 安全边界

- 原始文件按**不可信输入**处理：仅文本解析、不执行公式/宏/DDE、字段长度与行数受限；
- 每行保留 rawRowJson + 批次号 + 解析器版本，任何入账可回溯到原始行；
- 失败行明确计数并展示原因，不静默丢弃。
